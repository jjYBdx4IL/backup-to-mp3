[sweep] UPDATE 2026-08-04 (bug #1, RTTY): earlier runs of this report showed RTTY
[sweep] stuck at ~7.7% (1/13) at every bitrate. Root cause was a bug in
[sweep] bitrate_sweep.cxx, not a channel/compression/Baudot effect:
[sweep] progdefaults.rtty_autocrlf defaults true (page width
[sweep] progdefaults.rtty_autocount=72 chars, configuration.h:470-475) and was
[sweep] never disabled, so fldigi's RTTY TX was silently splicing a spurious
[sweep] CR+LF into nearly every ~75-77 char BLK line *before transmission*,
[sweep] corrupting the payload independent of bitrate. Fixed by setting
[sweep] progdefaults.rtty_autocrlf = false in bitrate_sweep.cxx's init block.

[sweep] UPDATE 2026-08-04 (bug #2, MFSK128L): after fixing bug #1, MFSK128L
[sweep] still showed a flat 342/345 (99.1%) from 112 down to 24kbps - this was
[sweep] ALSO not compression loss. MFSK128L's deinterleaver (interleave.cxx) is
[sweep] a cascade of depth=800 diagonal shift-registers chained on every
[sweep] symbol - a real ~25s fill-latency (roughly depth*symbits symbols)
[sweep] before the decode pipeline is warmed up, regardless of channel
[sweep] quality (mfsk.cxx:259, interleave.cxx:57-76). bitrate_sweep.cxx was
[sweep] sending real, counted blocks starting at t=0 with no warm-up, so the
[sweep] first few blocks always ate this cold-start transient - independently
[sweep] corroborated by task #2's finding of loss concentrated at the start of
[sweep] the MFSK128L segment in the real production pipeline too. Fixed by
[sweep] prepending 20 disposable "BLK 0" warm-up lines (never counted - see
[sweep] build_warmup() in bitrate_sweep.cxx) before the real numbered blocks,
[sweep] so the interleaver is primed before measurement starts. Result: 100.0%
[sweep] from 112 down to 32kbps; only at 24kbps and below does genuine
[sweep] compression-induced loss begin to show (99.7%, 99.4%, cliff to 49.0%
[sweep] at 8kbps). Conclusion updated: safe margin now extends to 32kbps, not
[sweep] 24kbps as previously reported - the earlier apparent floor at
[sweep] 24-32kbps was cold-start noise, not compression.

[sweep] ADDITION 2026-08-04 (FEC redundancy utilization): added metric avg/min
[sweep] columns above, sampled from modem::get_metric() (modem.h:154) - the
[sweep] live Viterbi decode-confidence value (0-100, mfsk.cxx:583-587), the
[sweep] same number fldigi's GUI shows as signal quality. Sampled per RX chunk
[sweep] in rx_from_wav(), skipping the first ~10% of the pass (preamble +
[sweep] warm-up + interleaver fill) to avoid the pre-decode zero.

[sweep] CORRECTION 2026-08-04 (the whole-run min/avg above is too coarse to
[sweep] be meaningful - do not read it as "early warning" of block loss):
[sweep] the initial version of this note claimed the declining avg at
[sweep] 32-24kbps was FEC "starting to earn its keep" ahead of block loss.
[sweep] That doesn't survive checking at block granularity. Added
[sweep] local_min_metric() to look at the metric specifically in the window
[sweep] each block was decoded in (not smoothed over the whole ~970s run),
[sweep] and compared lost blocks against surviving ones directly:
[sweep]   - @24kbps: lost block 344 local min = 16.2, TIED with the worst
[sweep]     surviving block's local min (16.2). No distinction.
[sweep]   - @16kbps: lost block 343 local min = 17.5, HIGHER than the worst
[sweep]     surviving block (16.8). The block that failed looked locally
[sweep]     *better* than blocks that succeeded.
[sweep]   - @8kbps: most of the 176 lost blocks (e.g. block 3: local min
[sweep]     47.2, block 250: 65.3) sit inside the surviving population's
[sweep]     normal range (avg 62.6, worst 19.5) - not locally depressed.
[sweep] Conclusion: the Viterbi path metric does NOT reliably predict which
[sweep] individual block fails. Likely reason: the metric measures how much
[sweep] the winning decode path beat its competitors, not whether that path
[sweep] is actually correct - under MP3's structured (non-Gaussian)
[sweep] quantization distortion, the decoder can land confidently on a wrong
[sweep] path, which looks identical in this number to a confident correct
[sweep] one. One thing the local view DID surface as real: at 8kbps the last
[sweep] 6 blocks (334, 337, 341, 343, 344, 345) show a clean, monotonic
[sweep] collapse - 39.8, 35.7, 20.8, 16.6, 12.6, 12.5 - a distinct end-of-run
[sweep] phenomenon (likely cumulative drift over the ~16min transmission at
[sweep] heavy compression), separate from the scattered mid-stream losses.
[sweep] Net: this metric is a reasonable coarse gauge of overall channel
[sweep] degradation trend (the whole-run average does decline smoothly with
[sweep] bitrate) but should not be used as a per-block risk predictor. RTTY's
[sweep] flat 5.3 avg/min at every bitrate is a separate, non-comparable
[sweep] quantity - rtty.cxx's raw tone-lock SNR formula (3000/delta *
[sweep] sigpwr/noisepwr, rtty.cxx:573), not an FEC-confidence signal, since
[sweep] RTTY has no FEC to measure the utilization of.

[sweep] ADDITION 2026-08-04 (airgap toggle): bitrate_sweep.cxx can now run
[sweep] each MP3-roundtrip WAV through harness/airgap_sim.py (the same
[sweep] speaker/mic acoustic-path simulator as task #5 - bandpass, soft-clip,
[sweep] echo, noise, optional dropouts/cutouts/repeats) before decode, so the
[sweep] sweep can measure bitrate sensitivity under a real acoustic path
[sweep] instead of MP3-only. Toggle: SWEEP_AIRGAP=1 (off by default - plain
[sweep] MP3-only sweeps are unaffected). SWEEP_AIRGAP_ARGS passes raw args
[sweep] through to airgap_sim.py; SWEEP_AIRGAP_SEED (default 0) keeps the
[sweep] same glitch pattern across all bitrates in one sweep so bitrate is
[sweep] the only thing varying. Airgap runs on the post-MP3 WAV, not the
[sweep] clean pre-MP3 WAV, matching the real pipeline order (compression at
[sweep] upload time, acoustic path at physical playback time).

[sweep] BUG FOUND AND FIXED while building this (bug #3, tail-fill latency):
[sweep] enabling airgap immediately exposed the SAME 3 blocks (343, 344, 345
[sweep] - the very last 3 of 345) failing at every bitrate from 112 down to
[sweep] 32kbps, completely independent of bitrate - the mirror image of bug
[sweep] #2's head cold-start problem, but at the tail. The deep interleaver's
[sweep] last real symbols run out of *future* context to spread against (the
[sweep] same reason the first symbols ran out of *past* context in bug #2),
[sweep] so they get less effective protection. mfsk.cxx's own flushtx()
[sweep] already drains this enough on a clean channel (hence bug #2's fix
[sweep] alone got 100% down to 32kbps with no airgap), but any real
[sweep] degradation re-exposes it. Fix: appended 20 disposable "BLK 0"
[sweep] cooldown lines after the real numbered blocks (build_warmup() reused
[sweep] for both ends - SWEEP_COOLDOWN_LINES to tune), same idea as the
[sweep] warm-up fix, mirrored. Verified: 342/345 -> 345/345 at 112kbps under
[sweep] baseline airgap conditions after the fix.

[sweep] mild REQUIREMENTS baseline - MP3 bitrate matters far less than the

[sweep] actually tested through a simulated speaker/mic path; recovery is
[sweep] dominated by acoustic-path glitches/degradation, not compression
[sweep] choice, and no bitrate choice fixes that - only the 3x repeat
[sweep] mechanism (task #2) does.
